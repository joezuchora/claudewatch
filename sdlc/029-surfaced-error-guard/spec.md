# Spec: close the set of surfaceable error messages

- **ID:** 029-surfaced-error-guard
- **Stage:** 2 — Design
- **Status:** draft
- **Date:** 2026-08-27

Reads `intent.md`. The design question it left open — runtime test, type-level constraint, or both —
is settled by a fact already written in this repo.

## The asymmetry this loop closes

`client.ts:180`, on the timeout flag, says:

> *Reading it from a flag beats parsing `err.message`, which varies by platform and Bun version and
> is **exactly the free text the telemetry allowlist exists to keep out** (sdlc/007, sdlc/010).*

Four lines later, `client.ts:200` assigns that same `err.message` to `FetchResult.message`. That
value is then:

1. **persisted to disk** as `lastErrorMessage` (via `enterCooldown` → `makeCacheEnvelope` →
   `writeCache`), and
2. **rendered to the user** twice — `format.ts:405` and `tooltip.ts:51`, both `Last error: ${...}`.

So the repo already identified this string as free text that must not escape into telemetry, built
an allowlist to keep it out, and then wrote it to the cache file and two tooltips. **The guard exists
on one path and not the other, and nothing records that as a decision.**

That asymmetry — not a hypothetical token leak — is what this loop fixes.

## Measurements this spec is built on

| Question | Measured |
|---|---|
| Messages `client.ts` can produce on HTTP failures | 4, all **constants**: `Authentication failed (401)`, `Rate limited (429)`, `Server error (${status})`, `Unexpected status ${status}` |
| Message on the network path | `err.message`, **uncontrolled** |
| What bun 1.3.11 puts there | `"Unable to connect. Is the computer able to access the url?"` for connection-refused, TLS failure and timeout alike — no URL, host or proxy credentials, with `HTTPS_PROXY` set |
| Tests covering §12's surfaced-error clause | **0** of `security.test.ts`'s 14 |

**Nothing sensitive reaches a surfaced error today.** This spec is therefore not remediation; it is
converting an accidental property into an enforced one.

## Behaviour

### B1 — the network path emits a constant, not `err.message`

```ts
message: timedOut ? 'Request timed out' : 'Network error',
```

Chosen by the same `timedOut` flag that already picks `failureClass`, for the reason `client.ts:180`
already gives. After this, **every message `fetchUsage` can produce is generated by this repo**, and
the set is finite and closed.

`err` is still used for nothing else on this path; the `catch` keeps its narrow scope (sdlc/014).

**This changes what one surface displays**, and that is a declared amendment to `intent.md`'s
"Not in scope: changing what any surface displays". On a network failure the tooltip's `Last error:`
line goes from `Unable to connect. Is the computer able to access the url?` to `Network error`.
Declared here, in Stage 2, rather than discovered in Stage 5 — loop 028 shipped an assertion inverted
against its spec with the decision recorded only in a code comment, and this is the same shape caught
one stage earlier. The information lost is nil: the string was already generic, and `failureClass`
(`timeout` vs `serviceUnavailable`) carries the distinction that matters.

### B2 — the closed set is named and exported

`packages/core/src/client.ts` exports a predicate over the finite set:

```ts
export function isSurfaceableMessage(m: string): boolean
```

Accepting exactly: the two auth/rate constants, the two new network constants, and the two
status-parameterised forms with a numeric status. Nothing else.

### B3 — a test that fails when the set is widened

`security.test.ts` gains a case that drives `fetchUsage` through **every** failure path — 401, 429,
5xx, unexpected status, network throw, timeout — with mocked HTTP, and asserts each resulting
`message` satisfies `isSurfaceableMessage`. A new producer that returns free text fails it.

### B4 — `SPEC.md §12` points at its own check

The clause gains a pointer to the enforcing test, so the invariant and its guard are not discoverable
only by grep. This is what `no-explicit-any` lacked for 27 loops.

## The redactor decision, recorded

**No redactor is built, and this is the reasoning rather than an omission.**

A redactor strips sensitive values out of a string that might contain them. After B1, no string that
reaches a surface can contain one — every message is a literal this repo wrote. A `sk-ant-` stripper
would defend a path no message travels, which is loop 028's characterization-test error repeated one
level up: **defence-in-depth is only depth if there is a first layer to be deep behind.**

Two facts make a redactor actively wrong here rather than merely redundant:

- The diagnostics modal's **first field is `__filename`**, an absolute path containing the user's home
  directory, displayed by design and sanctioned by `§17`. A redactor scrubbing paths out of the error
  string below it would be incoherent.
- The genuinely uncontrolled text on a surface is not an error at all: `enterprise.disabledReason`
  (`format.ts:369`) is free text from the API, rendered on the **success** path into every surface.
  A redactor scoped to errors would miss it entirely while appearing to have solved the problem.

`disabledReason` is **out of scope and recorded as open** — it is API-supplied content about the
user's own account, not a secret of a different kind, and constraining it is a separate design
question about rendering untrusted text.

## Edge cases

- **`String(err)` for a non-Error throw.** The current `: 'Unknown network error'` fallback is already
  a constant; B1 removes the branch entirely, so it cannot regress.
- **A cache file written by an older version** may already hold a free-text `lastErrorMessage`.
  `readCacheResult` does not validate it, so it will still render. Stated so it is not later claimed
  as covered; a migration is not proposed, because the values measured are harmless.
- **`main.ts:398`** writes `[claudewatch] fatal: ${err.message}` to **stderr**, not a surface. §12's
  clause is about surfaced errors, and stderr on a crash is a different question. Out of scope,
  recorded.
- **`Server error (${status})`** interpolates a number from the HTTP response. `status` is a
  `number` from `Response.status`, not attacker-controlled text.

## Acceptance criteria

- **A1** — `client.ts` contains no `err.message` on the fetch path:
  `grep -c "err.message" packages/core/src/client.ts` is **0**.
- **A2** — **the guard can fail.** Add a producer returning free text (e.g. change the 401 constant to
  include `err`-shaped text); `bun run verify` exits non-zero naming B3's test. Revert; green. **Both
  halves pasted into `review.md`** — a `review.md` showing only the green half fails this criterion.
- **A3** — B3's test drives all **six** failure paths and asserts on each. Six, counted, not "the
  failure paths".
- **A4** — mutation: delete any single arm of `isSurfaceableMessage`'s accepted set → exactly one
  test fails, and it is B3's.
- **A5** — `SPEC.md §12` names the test file and case.
- **A6** — the existing suite still passes with **no test's expectations edited to accommodate the new
  constants**. If a test asserted on `Unable to connect...`, that is a finding for `review.md`, not a
  silent edit.
- **A7** — the standing lint warning count is unchanged at 11, with no newly-firing rule.
- **A8** — every mutation in the plan's table produces its predicted count.

## Risks

- **A1's grep is a proxy.** `err.message` could return via a helper. A4's mutation is the real check.
- **A6 is the criterion most likely to be quietly violated**, because the natural response to a red
  test after B1 is to update its expectation. Any such edit must be reported.
- **The closed set can be widened legitimately** — a future failure class needs a message. B3 makes
  that a deliberate act (add to the set, and to the test) rather than an accident.
